# Этап 2: персональный учебный план

Реализовано 4 ноября 2026 года. Этап ограничен семидневным Premium-планом: платежи, AI API и движок проверки ответов не изменены.

## Поведение

`/learning-plan` показывает календарь и базовые рекомендации. Базовые рекомендации остаются бесплатными и открыты по умолчанию. Ссылка на календарь доступна в профиле, из блока рекомендаций и на странице Premium.

При первом открытии сервер составляет семь занятий начиная с текущего дня в часовом поясе профиля (по умолчанию UTC). Пять целей: общение, игры, путешествия, учёба, общий английский. Начальная цель берётся из существующих настроек. Нагрузка — 5, 10, 15 или 20 минут; по умолчанию 10. Каждый блок оценивается примерно в 5 минут; это ориентир, а не обещание длительности урока и не таймер. Завершённый урок не разбивается на новые попытки ради соблюдения времени.

Подбор использует существующий `learning_path_context`: предварительный CEFR, доступные опубликованные уроки, цели курсов, результаты и ошибки последних завершённых попыток, оценку навыков теста. `recommendLearningPath` сохраняет прежний лимит 12 для бесплатного маршрута; недельный план запрашивает до 28 блоков. Новые темы следуют зависимостям и доступной сложности; слабые навыки получают дополнительную практику. При недостатке новых тем используются повторы подходящих доступных уроков; если материала нет, день остаётся пустым с объяснением. В календарь не попадают ответы упражнений.

Практика запускает существующий урок с его действующими правами доступа и заданиями. Новых AI-упражнений и отдельного механизма оценивания нет. Пометка «сначала предыдущие уроки» — рекомендация, как и в существующей карте.

Семь дат фиксированы на время недели. Перенос меняет местами два занятия без выполненных заданий внутри этой недели, чтобы не удваивать дневную нагрузку. Прошедшие даты и дни с любым выполненным заданием переносить нельзя. Сам перенос сохраняет задания; повторное чтение без новых данных не перестраивает их. Новая цель, нагрузка или результаты могут обновить будущие незавершённые задания; перенесённые даты и выполненные задания сохраняются. При снижении нагрузки уже выполненные блоки не удаляются, даже если их суммарная оценка выше новой цели.

Смена часового пояса профиля не передатирует текущую неделю. После окончания семи дней создаётся новая неделя с текущим часовым поясом. Старые недели и их результаты сохраняются в базе; отдельного экрана архива на этом этапе нет.

## Автоматическое обновление и статистика

Триггер `voklumi_private.weekly_lesson_completed` реагирует на реальное завершение попытки. Успех от 60% засчитывает не более одного подходящего задания одной попыткой. Повторение одного урока в разные дни требует отдельных успешных попыток. Ранее пройденные, до назначения плана, уроки автоматически выполненными не считаются.

Любое новое завершение, включая неудачную попытку, инвалидирует рекомендации и увеличивает ревизию активной недели. Пересчёт выполняется при следующем обращении к календарю: при открытии, возвращении из урока, фокусе окна или проверке раз в минуту. Это ленивый пересчёт по свежим данным, без фонового AI или cron. Пройденные и прошедшие занятия не переписываются.

Статистика показывает выполненные задания/занятия и сумму оценочных минут выполненных блоков. Не считает сам факт открытия урока выполнением. Отдельного клиентского API «завершить занятие» нет.

## Хранение и защита

Миграция `20261104101518_weekly_premium_plans.sql` добавляет `weekly_plans`, `weekly_plan_days`, `weekly_plan_tasks`, служебные RPC и триггер. На всех новых таблицах включён RLS; `anon`, `authenticated` и `PUBLIC` не получают доступа. Существующая Telegram-сессия проверяется сервером, а RPC вызываются только служебным серверным клиентом. Публичные RPC — `SECURITY INVOKER` с фиксированным `search_path` и отозванным `EXECUTE`; серверный ключ не передаётся клиенту. Такой режим закрытого доступа соответствует [принципам RLS Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security).

`POST /api/weekly-plan` принимает только `refresh`, `settings` или `move`. Параметров пользователя, плана подписки, готового календаря или признака выполнения в запросе нет. Идентификатор берётся из проверенной сессии; все операции защищены проверкой источника. Право `lesson_review_plan` проверяется и в API, и заново в RPC по базе. Изменение клиентского Premium-статуса доступа не даёт.

Сохранение и перенос сериализуются блокировкой пользователя и проверяют ревизию. При сохранении дополнительно сверяется отпечаток учебных данных. Устаревший запрос получает конфликт, пересчёт повторяется максимум один раз. Перенос автоматически повторно не исполняется. После окончания Premium записи не удаляются; повторная активация в пределах недели восстанавливает тот же план. Независимый прогресс уроков не изменяется календарём.

## Выпуск

Миграция применена к проекту `wpctwlgfnkekgulgkxad` под версией `20261104101518`; серверная проверка вернула `weekly-v1 / ready: true`. Реальные планы, попытки или подписки для тестирования в проекте не создавались (после применения новая таблица планов пуста). Перед публикацией интерфейса выполнить `npm run weekly:check`. Проверка также включена в `build:production` и останавливает выпуск, если схема отсутствует или права клиентских ролей открыты. Реальные платежи должны остаться выключенными. Создание Premium для проверок выполняется только на изолированной тестовой базе.

## Проверки

- `tests/unit/weekly.test.ts`: правила подбора, бюджеты, слабые темы, зависимости, история, переносимые даты, строгий ввод; сохранение на PostgreSQL, ревизии, RLS/GRANT, центральный feature flag, часовой пояс, новая неделя, окончание подписки и повторная активация.
- `tests/weekly.spec.ts`: настоящий Next API с изолированной PostgreSQL-базой и Telegram-сессией, Free/Premium, CSRF, отсутствие доверия клиентскому userId, сохранение настроек, перенос, пересчёт после попытки, мобильная ширина 320px, доступность и закрытие UI после истечения доступа.
- `tests/production/build.test.mjs`: блокирование публикации без готовой схемы.

Проверка безопасности Supabase после применения: новых WARN нет. Три дополнительные INFO «RLS Enabled No Policy» относятся к закрытым серверным таблицам календаря; клиентские роли не имеют доступа, что дополнительно проверяет readiness RPC. См. [пояснение RLS без политик](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy). Сохранились прежние предупреждения об исполняемом helper `current_user_has_feature` в закрытой схеме для RLS ([anon](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable), [authenticated](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable)) и [защите паролей](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection); настройки авторизации не менялись.

Итоговые проверки: 142 unit-теста в 11 файлах; 5 браузерных сценариев на Next.js; отдельная проверка отображения календаря и запрета анонимных записей на локальном Worker; 10 тестов production preflight; Next.js и Cloudflare/Vite production build; TypeScript, ESLint и Prettier — успешно.

Worker UI-проверка использует явные тестовые ответы API. Сохранение и авторизованный API проверяются отдельно на настоящем Next API и изолированной PostgreSQL-базе. В локальный Worker production-секреты не переносились. Полная авторизованная проверка на опубликованном Worker относится к выпуску, а не к этому коммиту. Предупреждения сборщика об оптимизации lucide-imports и sourcemap плагинов остаются; сборка завершается успешно. Performance advisor для новых таблиц отмечает только ещё не использованный индекс на пустой таблице задач; индекс внешнего ключа сохранён.
