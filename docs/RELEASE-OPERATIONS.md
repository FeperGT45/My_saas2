# Эксплуатация Voklumi

## Публикация

Production: https://voklumi.voklumi67.workers.dev. Репозиторий `FeperGT45/My_saas2`, ветка `main` подключена к Cloudflare Workers Builds. Build: `npm run build:production`. Deploy: `npm run deploy:cloudflare && npm run telegram:setup`.

Перед сборкой проверяются Telegram `getMe` и готовность всех схем Supabase. Сборка останавливается при несовместимой базе. Секреты хранятся в Cloudflare Builds и передаются в runtime; их нельзя записывать в репозиторий. После отправки коммита дождаться успешного deployment именно этого SHA, затем выполнить `npm run release:check`. Проверка только читает публичные данные и проверяет запреты API; она не создаёт аккаунты или платежи.

Рабочий Supabase: `wpctwlgfnkekgulgkxad`. Миграции применять по порядку через migration tool/CLI. Не использовать `db reset` и не заменять production учебные таблицы локальным seed. Импорт библиотеки идемпотентен: текущий пакет revision 12 содержит 303 модуля / 2598 заданий, включая три архивных аудиомодуля. Опубликованы 300 полных уроков и один короткий вводный. Прогресс сохраняется по стабильным ID.

## Наблюдение и откат

Cloudflare Observability: 5% выборки логов вызовов, удаление query string, без traces и внешних получателей. В пользовательские логи не писать initData, cookie, ключи, тела платежей или ответы учеников. Проверять Issues/Observability при росте 5xx и после публикации. Само включение логов не заменяет внешний мониторинг доступности и оповещения: такой сервис и получатель оповещений пока не настроены.

При сбое приложения открыть Workers & Pages → voklumi → Deployments и вернуть предыдущую известную рабочую версию. Зафиксировать SHA проблемного релиза и причину, затем исправить код и отправить новый коммит. Откат Worker не откатывает базу. Новые индексы совместимы со старым Worker; удалять их при откате не требуется. Не удалять миграции из истории и не запускать обратные SQL-команды без проверки совместимости данных.

## Резервное копирование и восстановление

В Supabase → проект → Database → Backups проверить доступные копии, время последней копии и срок хранения для действующего тарифа. Не включать платный PITR без решения владельца. Для ручного копирования следовать [официальной инструкции CLI backup/restore](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore): установить Supabase CLI и Docker Desktop, взять Direct или Session pooler URI в Connect и настроить отдельное Postgres-подключение в защищённом окружении. Серверный Data API key не является паролем Postgres. Выгрузить роли, схему и **отдельно данные** (`--data-only --use-copy`): один schema dump не сохраняет прогресс пользователей. Историю миграций переносить по отдельному разделу инструкции. Не сбрасывать пароль БД ради этой проверки. Не включать URI с паролем в историю терминала или отчёт. Дампы содержат персональные данные: хранить зашифрованно, вне публичного репозитория и с ограниченным доступом. Если используется Storage, файлы объектов копировать отдельно от дампа базы.

9 ноября в авторизованной панели подтверждён Free-тариф без project backups. Это не настроенная резервная защита. Владелец должен выбрать ручное защищённое копирование с отдельным подключением Postgres или тариф с подходящей глубиной копий. Код приложения не может включить бесплатные платформенные копии на этом тарифе.

Проверять восстановление в отдельном проекте/базе, не поверх production. После восстановления сверить counts/checksums попыток, прогресса и XP, версии миграций, RLS/grants, отсутствие клиентского доступа к ключам ответов и подпискам. Только затем оценивать RPO/RTO. Настройку настоящей копии Supabase и её восстановление нельзя считать подтверждёнными одним локальным тестом.

`npm run test:recovery` проверяет отдельную PGlite-базу со всеми миграциями, учебным контентом и синтетической завершённой попыткой. Тест делает gzip backup, загружает его в новый экземпляр, сравнивает пять таблиц целиком и повторно проверяет ограничения доступа. Это проверка логики приложения и локального восстановления, не доказательство работоспособности Supabase Backups/PITR.

## Telegram Stars

Разовые тарифы: 49 XTR за 7 дней, 149 XTR за 30 дней, без автосписаний. Поддержка: https://t.me/feper145. Условия: `/premium/terms`. Неделя не оформляется как Telegram recurring subscription: этот API поддерживает период 30 дней. Premium выдаётся только после доверенного серверного `successful_payment`; клиентский callback доступа не даёт.

В production остаются `TELEGRAM_STARS_PAYMENTS_ENABLED=false`, `TELEGRAM_STARS_OWNER_REVIEWED=false`, `TELEGRAM_STARS_REFUNDS_ENABLED=false`. Локальные тесты транспорта и SQL не списывают Stars; `docs/stars-test.env.example` описывает только этот офлайн-режим. Отдельный официальный Telegram test environment с тестовым ботом и отдельным Supabase/Worker должен быть проверен до запуска продаж по [официальной инструкции](https://core.telegram.org/bots/payments-stars#testing-your-bot). Текущий транспорт приложения использует production Bot API, переключатель тестового endpoint ещё не добавлен. Не подставлять тестовый токен в production и не включать production-флаги ради теста. Не совершать реальную покупку без разрешения владельца.

## Проверка настоящего Android

В приложении Telegram открыть @Voklumi_bot → Mini App. Убедиться, что указан выполненный вход и собственный профиль. Пройти один бесплатный урок, запомнить XP, закрыть Mini App и открыть снова: прогресс и XP должны сохраниться. Проверить прокрутку карты, открытие словаря и экрана Premium, отсутствие горизонтального обрезания, отключение звука и уменьшение анимаций. Не нажимать подтверждение реальной оплаты. Зафиксировать модель телефона, версию Android/Telegram и наблюдения. Эмуляция ширины 320–390 px в Chromium не заменяет этот сценарий.

## Учебный контент и зависимости

Автоматическая проверка 300 уроков проверяет структуру, ответы, якоря и выполнение заданий. Отдельная оценка преподавателя английского не выполняется программой: нужен независимый рецензент и его замечания, прежде чем объявлять такую проверку завершённой.

Повторять `npm audit`, `npm audit --omit=dev`, lint и сборку при обновлении зависимостей. Известное предупреждение minimatch в инструментах ESLint остаётся открытым до совместимого исправления upstream. Не применять глобальный override на несовместимый major и не понижать Next.js ради формального исправления audit. Подробности: `docs/DEPENDENCY-REVIEW-2026-11-04.md` и актуальный отчёт релиза.
