# Этап A: первоначальная оценка английского

Это рабочая серверная система, а не UI-демо. Основные маршруты: `/placement`, собственный `/api/placement`, карточки на главной и в профиле. Прежние уроки, XP, серии, подписки и административная панель не заменяются. Никаких платных AI API нет.

## Что измеряет короткий тест

Банк `content/placement-en-ru.v1.json` содержит 120 авторских вопросов: 20 на каждый уровень A1–C2, из них 8 по грамматике, 6 по словарю и 6 по пониманию текстов. У каждого вопроса четыре варианта, один ключ, тема и краткое объяснение на русском. Тексты для чтения написаны специально для этого банка. Технические тесты проверяют полноту, уникальность, ключи и возможность серверной проверки; они не доказывают лингвистическую валидность уровня каждого задания.

Аудирование не оценивается: подходящих проверенных аудиоматериалов в проекте нет. Говорение и письмо также не оцениваются. Поэтому даже результат C2 означает только предварительную оценку по проверенным заданиям, а не владение всеми навыками на C2 и не сертификат. Ориентир описаний — [шкала CEFR Совета Европы](https://www.coe.int/en/web/common-european-framework-reference-languages/level-descriptions). Банк ещё не проходил психометрическую калибровку на выборке учащихся; для серьёзных решений нужна более полная проверка.

## Алгоритм grid-irt-v1

Сервер хранит распределение вероятностей по шести гипотезам уровня: A1=1 … C2=6. Начальное распределение — `[0.36, 0.26, 0.18, 0.11, 0.06, 0.03]`. Это явно заданный осторожный prior, а не обученная на персональных данных модель.

Для гипотезы уровня `k` и сложности вопроса `d`:

```text
P(верный ответ | k,d) = 0.25 + 0.72 / (1 + exp(-1.4 × (k-d)))
```

0.25 учитывает угадывание среди четырёх вариантов, верхняя граница 0.97 допускает случайную ошибку. При верном ответе веса умножаются на P, при неверном — на 1−P, затем нормируются. Все вычисления выполняет PostgreSQL в той же транзакции, что запись ответа. Значения параметров — проектные предположения, не эмпирически подобранные item-параметры. Число «определённость оценки» в UI — внутренняя posterior-масса модели, не измеренная вероятность успешной сдачи внешнего экзамена.

Первый вопрос всегда A1. Последующие категории чередуются: грамматика → словарь → чтение. Целевая сложность учитывает округлённое среднее распределения. После правильного ответа она остаётся прежней или повышается максимум на одну ступень; после ошибки снижается минимум на одну, кроме нижней границы A1. В целевой категории выбирается ближайшая доступная сложность; уже выданные ID исключаются. При одинаковой сложности порядок детерминированно перемешивается по случайному UUID попытки. Порядок вариантов тоже перемешивается, а ключ остаётся на сервере.

Публикация результата возможна только после 12 вопросов и завершается не позднее 20. Ранняя остановка требует:

- хотя бы трёх вопросов в каждой проверяемой категории;
- posterior-массы выбранного уровня не менее 0.8;
- центрального 80%-диапазона шириной не более одной ступени.

Уровень не выше максимальной предъявленной сложности. Для B2/C1/C2 дополнительно нужны минимум четыре правильных ответа не ниже предыдущей ступени (не ниже B1) и хотя бы один верный ответ в каждой из трёх категорий. При недостатке такого основания верхняя оценка ограничивается B1. После этого ограничителя проверяется условие ранней остановки. На лимите 20 вопросов возвращается предварительная оценка даже при широкой неопределённости; диапазон в UI включает выданную оценку. Один-два удачных ответа не создают высокий результат.

Результаты категорий — доля верных ответов в реально показанных заданиях, а не отдельный CEFR-сертификат. «Сильная сторона» означает минимум три вопроса и не менее 70% правильных ответов в категории этой попытки. Темы для улучшения извлекаются из допущенных ошибок.

## Хранение и защита

Пять новых таблиц: `placement_test_questions`, `placement_test_attempts`, `placement_test_answers`, `user_language_levels`, `user_skill_assessments`. Аналогичных сущностей в исходной схеме не было. В users добавлены только дата завершения onboarding и необязательный уровень учебного маршрута.

Все пять таблиц имеют RLS и закрыты для anon/authenticated. Приложение использует существующую серверную HttpOnly Telegram-сессию, поэтому прямые клиентские Supabase JWT-политики чтения здесь не выдаются. API берёт user ID только из проверенной сессии; служебные RPC доступны service_role, внутренние helpers закрыты и для прямого вызова этой ролью. Результат, уровень, правильность и XP не принимаются от клиента.

Старт и ответ блокируют пользователя и попытку в согласованном порядке. Одна активная попытка на пользователя/язык; одинаковые старты продолжают её. Уникальные пары attempt/question и attempt/request, сравнение сохранённого варианта и контроль текущего вопроса защищают от replay, изменения ответа и ответов не по порядку. До проверки клиент получает только ID, категорию, задание, текст и варианты. Объяснение и правильный вариант возвращаются после транзакционной записи ответа. API private/no-store, POST проверяет Origin, JSON, список полей и размер тела.

Текущий вопрос хранится как приватный снимок, поэтому изменение банка не меняет ключ уже предъявленного вопроса. Все ответы сохраняются сразу; перезагрузка возвращает следующий неотвеченный вопрос. Незавершённая попытка не истекает автоматически. Есть лимит пяти новых попыток за скользящие 24 часа; продолжение существующей попытки разрешено и при достижении лимита.

Тест не начисляет XP/монеты, не вызывает функции наград и не меняет `user_progress`. Retest сохраняет историю и навыки прежних попыток; только после нового завершения обновляется последняя оценка. Выбор «начать с нуля» создаёт A1 с источником `beginner`, без выдуманных ответов и skill-оценок; уже полученную адаптивную оценку эта операция не понижает. В UI после оценки менять маршрут можно отдельно.

Банк хранится в исходниках для импорта и воспроизводимого тестирования, не в React и не в public assets. В публичном GitHub-репозитории его можно изучить: это ориентировочный тест без прокторинга, а не экзамен с секретным банком. Серверная проверка защищает целостность записей, но не обещает выявлять заучивание или постороннюю помощь.

## Рекомендации и предварительные требования

Рекомендации вычисляются по настоящим опубликованным курсам/урокам английского и собственному прогрессу. Используются уровни courses, порядок units/lessons и действующий серверный Premium-доступ. Предшествующие опубликованные уроки курса должны быть зачтены (best_score ≥60%) для рекомендации следующего. Это предпосылки рекомендованного маршрута, а не новое постоянное ограничение движка уроков.

Сначала учитывается близость уровня, затем внутри него приоритет получают непройденные уроки. Уже пройденные подходящие материалы доступны для повторения с явной пометкой; они предпочтительнее слишком лёгких новых уроков. Если B1–C2 материалов ещё нет, UI честно показывает доступный более близкий курс, его реальный уровень и объясняет замену. При полностью пустом опубликованном каталоге сохраняется ссылка на каталог и объяснение, а не выдуманные уроки. Кнопка «Начать обучение» ведёт в настоящий `/lesson?lesson=UUID`. Поле english_route_level меняет рекомендации, не переписывая полученную оценку. Retest обновляет рекомендации и снимает старое ручное переопределение; пользователь может выбрать маршрут снова.

## Применение и импорт

Используются существующие Supabase URL / серверный ключ; новых секретов нет. В production локальная авторизация по-прежнему выключена. Последовательность:

1. Применить миграцию `20261103080420_placement_assessment.sql` после существующей схемы. В текущем проекте она уже применена 3 ноября 2026 через подключение Supabase.
2. Импортировать банк: `npm run placement:import` в защищённом окружении либо выполнить `supabase/placement-seed.sql` через административное подключение. Импорт транзакционный, upsert по стабильным code без дублирования. Пройденные уроки и профили не удаляются.
3. Проверить `npm run placement:check`. Требуются 120 активных вопросов, покрытие уровней/категорий, RLS и закрытые RPC/профильные поля. Обычный core db:check сохранён для прежних 22 таблиц; новая проверка отдельно проверяет пять placement-таблиц.
4. `npm run build:production` теперь проверяет и core, и placement до сборки Worker. Без миграции/банка новая публикация блокируется.

Для изменения контента редактировать JSON и выполнить `node scripts/import-placement.mjs --write-seed`, затем импорт. Правильные ответы не попадают в браузерный bundle. Нельзя переносить серверный ключ в NEXT_PUBLIC_*.

## Проверки

`npm run test:placement` / Vitest проверяет первый вход, skip, адаптацию, завершение, неопределённость, сохранение/продолжение, повтор запроса, конфликт ответа, изменения банка, историю, сохранность уроков, ручной маршрут, предпосылки, fallback, лимит попыток, приватность и RLS. `tests/placement.spec.ts` использует настоящий Next.js и HttpOnly-сессии с изолированным HTTPS PostgREST/PGlite-адаптером: автоматический onboarding на главной, A1, отсутствие повторного onboarding, профиль, полное прохождение, потерю ответа сети, reload/resume, retest, чужой аккаунт и axe-проверки мобильных экранов. Боевой пользователь не подменяется тестовой авторизацией.

Доступны прежние lint/typecheck, unit/regression, production Next build, Playwright и отдельная Worker-сборка/workerd. Реальный новый вход в физическом мобильном Telegram и психометрическая калибровка банка не заменяются локальными тестами. Этапы B–G не реализуются.

## Проверенное удалённое состояние

В проекте `wpctwlgfnkekgulgkxad` применена миграция `20261103080420_placement_assessment`, импортированы все 120 вопросов. `placement_database_status()` подтверждает `ready: true`, пять новых закрытых таблиц, покрытие A1–C2 и права RPC. Core readiness остаётся true. Существовавшие строки учебного прогресса и XP сохранены; тестовые пользовательские оценки в боевой базе не создавались. Security Advisor не обнаружил новых публично вызываемых SECURITY DEFINER-функций: все placement RPC закрыты для клиентских ролей. INFO об RLS без политик на этих пяти таблицах соответствует намеренному запрету прямого клиентского доступа.

## Результат проверок этапа A

Пройдены lint, TypeScript, Prettier, 40 Vitest-тестов (18 по placement), все прежние SQL/security-наборы, production Next build и 30 Playwright-тестов на нём. Worker build, dry-run и те же 30 браузерных тестов также пройдены. Два placement-сценария проверяют настоящие Next API с HttpOnly-сессией и локальным HTTPS PostgREST/PGlite; отдельный сценарий запускает placement-клиент на выбранном runtime (включая workerd) с SQL-backed подменой транспорта. Уникальный маркер банка не найден в клиентских assets Next/Worker. Полный вход с нового физического устройства Telegram и внешняя калибровка CEFR не заявляются как выполненные проверки.

Дополнение `20261103082824_placement_route_priority.sql` применено к той же базе: сначала близость уровня, затем новизна урока, с пометкой повторения. Повторная проверка core/placement readiness успешна. Для нового окружения применяются обе миграции этапа A.
