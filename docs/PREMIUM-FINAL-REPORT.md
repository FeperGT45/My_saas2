# Voklumi Premium — итоговый отчёт

Дата: 5 ноября 2026 года. Изменения подготовлены в существующем приложении; реальные покупки не включались, публикация Worker не выполнялась.

## Готовые возможности

- Сохранены ранее реализованные учебный план, аналитика, словарь, интерактивные истории, тренировки слабых тем и испытания. Экран Premium связывает все восемь разделов, сравнивает Free/Premium и показывает реальный компонент оформления в режиме предпросмотра.
- Оформление: исходная Voklumi Dark, бесплатные Slate/Ocean, Premium Midnight Purple/Cyber Blue/Neon Green/Sunset/Sakura; рамки, значки, эффекты завершения и украшения профиля. Выбор хранится на сервере с контролем версии. Рейтинг получает только разрешённое публичное оформление. После окончания Premium выбор сохраняется, но сервер возвращает бесплатное оформление; при повторной активации платный выбор снова действует.
- Лёгкие CSS-анимации ограничены по длительности; `prefers-reduced-motion` и `update: slow` отключают эффекты. Нет новых тяжёлых библиотек или внешних платных API.
- Расширенное тестирование: 36 вопросов, по 12 на грамматику, лексику и чтение, адаптация сложности на основе существующей модели первоначального теста. Используется существующий банк проверенных вопросов, без генерации заданий. Ответы оценивает сервер; правильные варианты скрыты до завершения. Есть возобновление, разбор всех ответов, последние 20 результатов, сравнение двух последних и рекомендации доступных уроков. Два новых теста за 24 часа — техническое ограничение; активный можно продолжить. Исходное бесплатное тестирование и прогресс не переписываются.
- Результат — предварительный ориентир, не официальный экзамен или сертификат CEFR. Говорение и письмо не проверяются. Аудирование отсутствует: проверенный аудиоматериал не подключён. Проценты разных адаптивных наборов не выдаются за точное измерение роста знаний.
- Серверные API используют существующую Telegram-сессию, проверку источника запросов и Premium-права. Клиент не передаёт доверенный Premium-статус или чужой user ID. Таблицы ответов закрыты для клиентских ролей; серверный ключ не входит в клиентский код.

В этой рабочей папке нет `.env.local` с серверными ключами, поэтому прямой CLI-запуск `premium:expansion-check` без конфигурации ожидаемо остановился. Готовность удалённой схемы проверена через подключение Supabase; локальные API проверяются с изолированной базой, а не с аккаунтами пользователей.

Security Advisor показал прежние предупреждения:

- RLS без клиентских политик у серверных таблиц (включая новые ответы/попытки) — намеренный запрет прямого доступа. [Объяснение Supabase](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy).
- `current_user_has_premium()` — существующая функция для RLS, доступная anon/authenticated: не принимает ID, проверяет только собственный `auth.uid()`. Доступ нужен действующим политикам чтения уроков. [Диагностика SECURITY DEFINER](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable).
- Выключена проверка утёкших паролей Supabase Auth. В пользовательском входе применяется Telegram, парольный вход приложение не предоставляет. Если он будет включён, настройте [защиту паролей](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

## Telegram Stars: реализованная модель

Предложение приложения — **разовая покупка доступа на 30 дней, без автоматического списания**. Следующую покупку пользователь запускает сам. Цена не выдумывается: её задаёт владелец. Пока конфигурация не завершена, покупка недоступна.

Для цифровых товаров используются `XTR`, пустой `provider_token` и одна позиция цены. Заказ связывает непрозрачный payload, пользователя, сумму и валюту. Клиентское событие `paid` только обновляет статус; доступ выдаётся после доверенного серверного `successful_payment`. Проверяются секрет webhook, плательщик, сумма, валюта, payload и уникальный charge ID. Повторная доставка не создаёт второй доступ. Возвраты обрабатываются сервером, в том числе с учётом перестановки событий. Отмена покупки ничего не выдаёт; подтверждённый доступ восстанавливается повторным чтением серверного статуса.

Telegram поддерживает также регулярные Stars-подписки через `subscription_period=2592000` и управление продлением через `editUserStarSubscription`. Эта отдельная модель здесь **не включена**: параметры регулярного платежа отклоняются, интерфейс честно сообщает об отсутствии автопродления. Официальные источники: [Stars для цифровых товаров, подтверждение и возвраты](https://core.telegram.org/bots/payments-stars), [createInvoiceLink](https://core.telegram.org/bots/api#createinvoicelink), [editUserStarSubscription](https://core.telegram.org/bots/api#edituserstarsubscription).

Сохранены обработчики `/terms`, `/paysupport` и отдельная операторская команда возврата. Необходимы реальные опубликованные условия покупки, канал поддержки и рабочая процедура рассмотрения возвратов.

Безопасная конфигурация описана в `stars-test.env.example`: оба разрешающих флага равны false. Сумма 99 используется только в изолированном тесте и не является утверждённой ценой. Автоматические проверки моделируют доверенные/поддельные события на локальном сервере с тестовой базой; они не отправляют запросы оплаты в Telegram и не списывают Stars. Отдельная покупка в Telegram test environment и реальные платежи не проверялись.

## Настройка и публикация

1. Отправить подготовленный коммит в подключённую ветку GitHub после проверки изменений. В этой задаче push и публикация не выполнялись.
2. Cloudflare → Workers & Pages → `voklumi` → Settings → Builds: использовать `npm run build:production`, Node 24 из `.node-version`. Новая проверка схемы останавливает публикацию, если Premium-таблицы не готовы. В текущем Supabase миграция уже применена; в других окружениях сначала применить миграции и импортировать существующий банк placement-вопросов.
3. В Build Variables/Secrets настроить `APP_URL`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, секреты `SUPABASE_SECRET_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`. Использовать существующую схему переноса серверных настроек в Worker из `PRODUCTION.md`; секреты не записывать в Git или `NEXT_PUBLIC_*`. Проверить правильное имя бота `TELEGRAM_BOT_USERNAME` и соответствие бота Mini App.
4. Для Stars указать `TELEGRAM_STARS_PREMIUM_PRICE` (положительное целое число, ограничение сервиса 1–10000), HTTPS-адреса `PREMIUM_TERMS_URL` и `PAYMENT_SUPPORT_URL`. Отдельный платёжный provider token для Stars не требуется. Оставить `TELEGRAM_STARS_PAYMENTS_ENABLED=false` и `TELEGRAM_STARS_OWNER_REVIEWED=false` до явного разрешения владельца.
5. После публикации выполнить `npm run telegram:setup`: проверить, что webhook указывает на `/api/telegram/webhook`, совпадает его секрет и принимаются `message` и `pre_checkout_query`. Проверить вход через настоящий Telegram, сохранение урока, Free/Premium и восстановление сессии. Локальные проверки не подтверждают текущие production bindings.
6. Сначала отдельно проверить покупку и возврат в официальном тестовом окружении Telegram, на отдельном боте и отдельной базе. Проверить поддержку и тексты условий. Только после разрешения владельца включить оба флага реальных покупок и пересобрать/опубликовать Worker. Для операторских возвратов существует дополнительный `TELEGRAM_STARS_REFUNDS_ENABLED`; его включать отдельно по утверждённой процедуре.

Реальный телефон не использовался. Мобильная проверка в этой задаче выполняется в Chromium с узким viewport и уменьшением анимаций; производительность на физическом слабом Android требует отдельной проверки.
