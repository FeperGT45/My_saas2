# Premium: архитектура доступа, этап 1

Реализовано 4 ноября 2026 года. Публичные тарифы — Free и Premium. Платежи и AI API в этом этапе не включались. Изменения приложения сохраняются локально; миграция Supabase применена как `20261103215202_premium_permissions`.

## Структура и источник истины

Используется существующая таблица `subscriptions`, а не параллельная система подписок. В ней остаются `user_id`, `plan`, `status`, `starts_at`, `ends_at` и связь с существующим Stars-заказом. Free — отсутствие действующего подтверждённого Premium, отдельную строку Free создавать не нужно. Старые строки plus/pro сохранены и не получают дополнительных прав: до этого этапа проверка Premium тоже их не учитывала.

Premium действует только при `status=active` и `starts_at <= now() < ends_at`. Источник должен быть подтверждён: существующий Stars-заказ того же пользователя со статусом paid/refund_pending либо явно выданная доверенным сервером активация с `grant_reason`. Просто вставленная строка premium без подтверждённого источника не предоставляет доступ.

`has_premium(user)` — единая проверка действующего периода. `has_feature(user,key)` дополнительно проверяет централизованный каталог `subscription_features`: флаг enabled и минимальный тариф. Каталог и операции выдачи доступны только доверенной серверной роли. Клиент не выбирает user_id для этих операций.

| Право               | Что защищает                                                               |
| ------------------- | -------------------------------------------------------------------------- |
| premium_courses     | Платные курсы; явно открытые free_preview остаются доступными              |
| extra_exercises     | Дополнительные задания при создании попытки и при продолжении существующей |
| advanced_statistics | Платная статистика                                                         |
| lesson_review_plan  | Платный план повторения уроков                                             |

Последние два права нужны вместе для существующего объединённого `/api/premium/features`, поскольку он возвращает и статистику, и план. Обычные уроки, базовая статистика, XP и интервальное повторение слов сохраняют текущую доступность Free.

## Сервер и база данных

- `/api/premium` читает сессию Telegram на сервере и возвращает plan, status, даты периода, серверное время и рассчитанные права. Произвольные query-параметры отвергаются. Изменяющего подписку HTTP-метода у этого API нет.
- `/api/premium/features` использует `requirePremiumFeature` и повторную проверку в самом SQL RPC. Заголовки, локальное состояние и присланный premium=true не предоставляют права. Ошибка проверки закрывает доступ.
- Уроки продолжают использовать существующие защищённые RPC. `can_access_lesson` проверяет право premium_courses, а существующий движок использует extra_exercises для снимков и продолжения. Миграция меняет конкретный предикат в известных функциях и прерывается, если ожидаемый исходный предикат отсутствует; остальной движок сохраняется.
- RLS-политики используют helper в неэкспонируемой схеме `voklumi_private`. Он вычисляет право только для `auth.uid()`, не принимает произвольный user_id и не создаёт новый публичный SECURITY DEFINER RPC.
- Таблица флагов имеет RLS без клиентских политик и закрытые клиентские привилегии. Существующая политика чтения собственных подписок сохранена; новый grant_reason клиентам не раскрывается. Запись подписок и флагов из браузера запрещена.
- Секретный клиент Supabase остаётся в модулях `server-only`. Общий файл permissions содержит только типы и названия прав. Ответы личных API используют Cache-Control: no-store.

## Окончание, отмена и повторная активация

Срок проверяется по времени БД при каждом обращении. Cron и изменение строки с active на expired не требуются для прекращения доступа: просроченный active уже не даёт Premium. API отражает effective status expired. cancelled и refunded также не дают прав. Будущий период отражается как scheduled без раннего Premium-доступа.

История подписок не удаляется. Уроки, результаты, XP, слова, расписание повторений и пользовательские настройки не очищаются при окончании или отмене. Существующая защита незавершённого платного урока продолжает проверять действующий доступ на каждом шаге; история завершённого обучения остаётся сохранённой.

Внутренний `grant_premium_access(user, request, days, reason)` позволяет доверенному серверу выдать или повторно активировать Premium без платежа. HTTP-эндпоинта для него нет. Операция принимает 1–366 суток по 24 часа, требует причину, блокирует строку пользователя и использует request UUID для идемпотентности. Повтор тех же параметров не продлевает доступ; изменение параметров с прежним UUID отвергается. Новая активация после истечения создаёт новый период; при действующем/запланированном доступе добавляется следующий период. Повтор старого запроса не отменяет последующую отмену подписки.

В production никто не получил такую активацию во время разработки. Все тестовые подписки выдавались только в PGlite.

## React

`usePremium()` возвращает `status`, `loading`, `error`, `refresh()` и `can(feature)`. Он уже используется экраном Premium. `can()` предназначен только для отображения элементов: окончательное решение принимает API/БД.

Данные привязаны к аккаунту; при смене пользователя или выходе прежние права не отображаются. Запросы отменяются при размонтировании. Состояние проверяется повторно не реже минуты при успешных ответах и на границе окончания/начала периода. Для локальной оценки оставшегося времени используются время сервера и монотонный таймер, а не часы пользователя. При ошибке права считаются неподтверждёнными; доступна ручная повторная проверка.

## Миграция и выпуск

Миграция уже применена в подключённом Supabase; проверено `premium_permissions_status(): { version: permissions-v1, ready: true }`. В каталоге 4 права; anon/authenticated не могут вызвать выдачу Premium, а production-активаций с grant_reason — 0. Advisor не добавил новых предупреждений: новая таблица намеренно закрыта клиентам, RLS helper находится в приватной схеме.

`npm run premium:check` проверяет готовность каталога и права таблиц/RPC. Production preflight вызывает её до сборки Worker и блокирует публикацию при ошибке. Само приложение ещё не опубликовано. Флаги реальных платежей в Cloudflare по-прежнему false. Исправление входа в cross-site Telegram Web остаётся отдельной задачей вне этого этапа.

## Проверки

- 128 Vitest-тестов: в том числе 10 новых проверок Free, подтверждённого источника, выдачи, окончания, повторной активации, будущего периода, отключения прав, RLS, защиты от самостоятельной записи и готовности схемы.
- 42 браузерных сценария прошли. Новый сценарий использует настоящий Next.js API и изолированную SQL-БД: проверяет поддельные заголовки и параметры, Free → Premium → окончание → повторная активация, автоматическое обновление хука, сохранность прогресса и выключенные платежи.
- 10 тестов preflight/обновления старой БД прошли, включая остановку при отсутствии Premium permissions.
- Регрессии основного доступа БД и существующих Stars-подписок прошли; 4 Node-теста платежей прошли. Настоящие платежи не выполнялись.

TypeScript и ESLint прошли. Production-сборки Next.js и Cloudflare Worker прошли. На свежем Worker дополнительно прошли 5 сценариев: отказ анонимным запросам/поддельным ролям, закрытый health endpoint, отображение статуса Premium с изолированными SQL-данными и выключенная оплата. Это не авторизованная проверка production-платежа: локальный Worker не использовал production-секреты. После финальной сборки отдельно повторно прошли 3 Premium-сценария на Next.js, включая потерю доступа к серверной проверке.

Изменённые файлы сгруппированы в `src/lib/premium`, `src/features/premium`, двух существующих Premium API, новой миграции, `scripts/check-premium.ts` и preflight. Добавлены `tests/unit/premium.test.ts`, `tests/premium-access.spec.ts`; обновлены соответствующие фикстуры и проверки подготовки релиза. Проверка физического телефона не выполнялась.
