# Конфиденциальность и мониторинг Voklumi

16 ноября 2026. Поставка выполняет пункты 2 и 3 подготовки к запуску; платёжные тарифы и доступ к материалам не меняются.

## Конфиденциальность

Публичная страница `/privacy` описывает реально сохраняемые данные Telegram, учёбы, повторений, приглашений, настроек и платежей. Указан контакт владельца @feper145, cookie/localStorage, роль Telegram/Supabase/Cloudflare/GitHub и ручной порядок обращения за исправлением или удалением. Не обещаются несуществующее мгновенное удаление, неизвестные сроки хранения либо полная оценка всех языковых навыков. Юридическое наименование/адрес владельца и применимая юрисдикция не выдумываются; владелец может дополнить их своими действительными данными.

Ссылка есть в настройках и условиях Premium. Команды `/privacy` и `/delete_account` дают ссылку на страницу, не удаляют профиль. Страница доступна без входа; подтверждённая заявка создаётся только из действующей Telegram-сессии.

POST `/api/privacy/deletion` принимает только requestId и confirm=true. user_id берётся сервером из сессии. Проверяются Origin, размер тела и поля. Один открытый запрос на пользователя, идемпотентность по UUID и транзакционная блокировка не дают создавать дубли при потере ответа. GET возвращает только последнюю собственную заявку. Данные, XP и оплаченные периоды не изменяются.

Заявки доступны администратору в `/admin/privacy`, переход из `/admin`. API списка проверяет серверный allowlist, а не роль из браузера. Записи в `privacy_deletion_requests` закрыты для anon/authenticated; обработку выполняет владелец. Публичная форма — **заявка**, не кнопка немедленного удаления.

После получения заявки владелец проверяет принадлежность аккаунта, уточняет объём удаления и вопросы возврата, фиксирует статус processing и выполняет согласованную обработку в защищённом окружении. Нельзя помечать completed до фактической обработки. Финансовые квитанции, необходимые для возвратов/споров, рассматриваются отдельно; отправка заявки не является возвратом или отменой Stars. Этот релиз не выполняет массовое/автоматическое удаление пользователей. При невозможности входа доступен контакт поддержки из того же Telegram-аккаунта.

## Уведомления

Основной получатель — **первый администратор из защищённого ADMIN_USER_IDS**. Telegram ID читается только сервером из его профиля. Новые bot token, ключ Supabase или общий секрет в GitHub не копируются. Получатель должен ранее открыть бота, иначе Telegram может отказать в доставке; это вызывает резервный инцидент GitHub.

GitHub Actions `.github/workflows/monitor.yml` каждые приблизительно 15 минут независимо от Worker проверяет `/api/health` и защищённую серверную диагностику базы/платежей. Полный каталог не скачивается на каждом запуске, чтобы не расходовать бесплатный трафик Supabase. Используются стандартные GitHub-hosted runner и встроенный GITHUB_TOKEN. Репозиторий публичный; платные сервисы не подключаются. Расписание GitHub может задерживаться, а после длительной неактивности публичного репозитория — отключаться; это не SLA внешнего uptime-провайдера. Проверять, что workflow включён в Actions.

Серверная `/api/ops/check` проверяет БД, новую схему, конфигурацию оплаты и Telegram getWebhookInfo: URL, allowed_updates, недавние ошибки доставки. Также читает фиксированные счётчики ошибок webhook, создания счёта, серверных API и новые заявки о данных. Тексты исключений, тела запросов, initData, user ID, ответы и квитанции в журнал не записываются.

Авторизация machine endpoint — GitHub OIDC RS256 через публичный JWKS. Проверяются issuer, audience, времена, immutable ID репозитория/владельца, точный workflow_ref, main и разрешённый тип запуска. Токен форка, PR, другого workflow или истёкшая подпись не подходят. JWT не выводится в CI-логи. У GitHub нет ключей БД или бота.

Telegram получает один первый сигнал готовности, затем сообщения о сбоях и новых заявках. Транзакционные leases ограничивают повторные сообщения (обычно 30 минут); устаревший процесс не может подтвердить новую lease. Недоставленное сообщение доступно для повторной попытки через две минуты, фактически на следующем запуске проверки.

При полном отказе Cloudflare или Supabase отправка Telegram через приложение тоже может быть недоступна. **Независимый резерв — GitHub Issue с упоминанием владельца** и неуспешный запуск Actions. Открытый инцидент не дублируется на каждом запуске; после восстановления закрывается, при повторном сбое открывается заново. В публичном Issue только технические пути/HTTP-статусы и ссылка на workflow. Email/push GitHub зависят от личных настроек уведомлений владельца.

Закрытая страница `/admin/operations` показывает счётчики и подтверждение первого сообщения Telegram. При ошибке смотреть GitHub Actions → Voklumi availability, Cloudflare Observability и Supabase. Защиту webhook и обработку уже оплаченных квитанций не отключать ради мониторинга.

## База и публикация

CLI создал миграцию; после применения имя выровнено с историей Supabase: `20261116111950_privacy_and_operations.sql`. Также применена добавочная `20261116113059_ops_notification_watermark.sql`: счётчик подтверждённых событий не даёт потерять новую ошибку во время доставки предыдущего сообщения. Миграция `20261116114923_ops_retry_delivery_state.sql` также не позволяет старой успешной доставке скрыть неуспешную повторную попытку. Готовность — privacy-ops-v3. Добавлены три таблицы, индексы и только SECURITY INVOKER RPC для service_role. Прямые клиентские grants отозваны; RLS включён. `privacy_ops_status` проверяет таблицы и ACL; `npm run ops:check` блокирует сборку production при отсутствующей/небезопасной схеме.

Миграция применена в рабочем Supabase, readiness=true. Число профилей, строк прогресса, попыток, XP-событий и заказов до и после совпало; созданных тестовых заявок в рабочей базе нет. Существующие функции и строки не удалялись. Старые предупреждения Supabase Advisor о current_user_has_premium и защите паролей остаются прежними; новые серверные таблицы намеренно имеют RLS без клиентских политик.

Первый запуск workflow происходит после push изменений мониторинга; повторные попытки дают Cloudflare время закончить deployment. После успеха ожидается первое сообщение Telegram и запись delivered_at для monitor_ready. Ручной повтор: GitHub → Actions → Voklumi availability → Run workflow. Это запускает проверки, а не создаёт тестовую покупку или заявку.

## Проверки

- SQL/PGlite: чужой аккаунт, сохранность профилей/прогресса, повторные заявки, закрытые таблицы/RPC, агрегация кодов, гонки leases и повтор доставки.
- Криптографические тесты OIDC: действующая RSA-подпись, подмена payload, алгоритма, audience, репозитория, workflow, ветки и времени.
- Монитор: ошибки HTTP/сети, некорректный JSON, один Issue на инцидент, восстановление и отказ редактировать чужой Issue.
- Реальные изолированные API: заявка с подтверждением, отказ подмене userId и Origin, повтор после перезагрузки, сохранение прогресса, разграничение административной очереди.
- Мобильная страница политики 320 px; регрессии авторизации, администратора и checkout.

Для полного импорта 303 модулей в PGlite локальный лимит одного ранее пятисекундного теста повышен до 15 секунд после превышения на 0,1 секунды под параллельной нагрузкой. Утверждения о сохранности старого контента и повторе без записи сохранены. Итоговый полный прогон: 214 unit/integration-тестов прошли; production-preflight — 18 Node-тестов.

TypeScript, ESLint, Prettier, production Next.js build и Cloudflare build прошли. 10 браузерных сценариев проверили реальные изолированные API, админку, форму/политику и checkout. Отдельно подтверждено скрытие закрытых страниц после выхода и возврата по истории браузера. Платёжные SQL-регрессии, Node-тесты авторизации, Supabase и администрирования прошли.
