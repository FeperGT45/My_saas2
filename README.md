# Voklumi

Основа SaaS-приложения для изучения языков в Telegram Mini App. Мобильный интерфейс на русском, расширяемая архитектура, без платных API. Текущий этап — серверный движок уроков с Telegram-авторизацией и сохранением результатов. Остальная игровая оболочка использует демоданные.

## Быстрый старт

Требуется Node.js 22.13+ (рекомендуется Node.js 24 LTS) и npm.

```bash
npm ci
cp .env.example .env.local
npm run dev
```

Откройте http://localhost:3000. Без переменных Supabase приложение также запускается. Локальный деморежим включается только при `NODE_ENV=development` и `NEXT_PUBLIC_ENABLE_LOCAL_DEMO=true`. Перезапустите сервер после изменения env. Не выставляйте dev-сервер в публичную сеть.

```bash
npm run lint
npm run typecheck
npm run format:check
npm run build
npm start
```

## Стек

Next.js App Router, React, TypeScript strict, Tailwind CSS 4, shadcn/ui (конфигурация и локальный Button на Radix/CVA), Motion, Lucide, Supabase JS, Telegram Mini Apps SDK (`@tma.js/sdk-react`). Версии зафиксированы в package-lock.json. Шрифты системные: сборка не зависит от загрузки Google Fonts.

Маршруты: `/` (главная), `/learn` (карта), `/courses` (каталог), `/lesson` (серверный урок), `/leaderboard` (рейтинг), `/achievements`, `/profile`, `/settings`, `GET /api/health`. Дополнительно предусмотрены 404, loading и error boundary. Нижняя навигация учитывает safe-area; анимация учитывает reduced motion. Язык документа — `ru`; словари подключаются через `getDictionary`. Новые локали следует добавить в реестр и затем реализовать выбор/маршрутизацию локали. Сейчас доступен только русский интерфейс.

## Telegram и безопасность

SDK инициализируется только в браузере: mount/ready, расширение viewport, CSS-переменные safe-area. Back Button скрыта на главной, на уроке ведёт к карте, из настроек/достижений — в профиль, с остальных экранов — на главную. Используются доступные методы SDK, есть браузерный fallback.

`POST /api/auth/telegram` принимает **только** `initData`. Сервер проверяет HMAC-SHA256 по bot token с constant-time сравнением, запрещает дубли ключей и некорректный hash, ограничивает размер тела, проверяет auth_date (не старше 5 минут, не более 30 секунд в будущем) и форму пользователя. Telegram ID, имя, username и HTTPS URL аватара извлекаются только после проверки подписи. `initDataUnsafe` не используется для доверенных данных.

В Supabase создаётся отдельная внутренняя Auth identity без доступного пользователю пароля и профиль `users`; атомарная RPC сохраняет профиль и серверную сессию. Сессия — случайный 256-битный токен в HttpOnly SameSite=Lax cookie (Secure и __Host-prefix в production), в БД хранится только SHA-256 токена. Срок — сутки, без автоматического продления. Подписанный initData hash уникален: повтор без действующей сессии отклоняется. Повторный запрос из уже авторизованного браузера допускается после повторной проверки подписи и совпадения identity.

`GET /api/auth/session` — защищённая точка чтения собственного аккаунта (401 без сессии); аккаунт и его серверный прогресс отображаются в профиле. `POST /api/auth/logout` удаляет запись сессии и cookie. Auth POST-запросы проверяют Origin по `APP_URL`; ответы аккаунта не кэшируются. Сессия Telegram не является Supabase JWT: браузеру не выдаются service key или привилегии RLS. Для будущих защищённых маршрутов вызывайте `getSessionUser(request)` и выбирайте данные **только** по возвращённому user ID. Не используйте присланный клиентом ID и не передавайте произвольные запросы в adminClient.

Инициализация Telegram и успешная серверная авторизация — разные состояния. При ошибке входа интерфейс остаётся доступен как явное демо. Главная остаётся демонстрационной; профиль, достижения и результаты уроков работают с серверными данными. Реальный вход требует миграции 003 и Supabase service key; без них endpoint возвращает 503, не подменяя вход тестовой учётной записью.

## Supabase

`getSupabaseClient()` возвращает `null`, пока не заданы URL и publishable key. Клиент не используется для имитации записи данных; сессии в браузере пока не сохраняются. `NEXT_PUBLIC_*` публичны. `TELEGRAM_BOT_TOKEN` предназначен только для будущей серверной интеграции. Service-role ключи никогда не добавляйте в клиентские env.

Схема, RLS и миграции находятся в `supabase/`; инструкция ниже. Для работы с личными данными ещё потребуется связать проверенную сервером Telegram-сессию с Supabase Auth. Publishable key сам по себе не является пользовательской авторизацией.

## Границы этапа

Восемь экранов в тёмной космической теме. Авторский маскот Ри — кристальный скат-комета, нарисованный SVG-компонентом `src/components/ui/mascot.tsx`, без внешних ассетов и персонажей. Объёмные кнопки, прогресс-бары, состояния загрузки/ошибки и пустые результаты поиска.

Движок `/lesson` загружает упражнения из БД и сохраняет результат на сервере. Карта и главная пока не отражают реальные результаты уроков; профиль и достижения показывают серверные значения. Прогресс главной и карточки курсов — фикстуры в `src/features/demo/data.ts`; они не связаны с Supabase, Telegram-пользователем или будущим API. Каталог фильтруется по названию, вкладка друзей показывает пустое состояние. Переключатели настроек — явный UI-пример, не управляют устройством и не сохраняются. Системный reduced motion учитывается независимо.

Уроки начисляют серверный XP и сохраняют прогресс. Подготовлена оплата Premium через Telegram Stars, выключенная до проверки владельцем (см. раздел ниже); реальные рейтинги описаны в разделе социальных функций. Платные сервисы не подключены. Локальные демоэкраны доступны также в production как обзор; это не обход авторизации.

## PostgreSQL / Supabase

Миграции подготовлены для Supabase PostgreSQL 17. Удалённая база настроена и проверена — см. [актуальный статус](docs/SUPABASE_DEPLOYMENT.md). Постоянные секретные привязки окружения не создавались. Локальные проверки используют PGlite (PostgreSQL в WASM), подставляя только `auth.users`, `auth.uid()` и роли Supabase. Это проверяет SQL и RLS, но не заменяет интеграционную проверку Supabase Auth/PostgREST.

### Локальный запуск Supabase

Установите Supabase CLI и Docker по официальной документации. Из корня проекта:

```bash
supabase start
supabase db reset
supabase status
```

`db reset` удаляет локальные данные, применяет миграции по порядку и `supabase/seed.sql`. Seed содержит только публичный каталог и достижения; пользователей Auth, платежей и секретов там нет. Не используйте reset для базы с нужными данными. Скопируйте URL и publishable/anon key из локального Supabase в `.env.local` по `.env.example`. Секретный service-role key нужен только доверенным серверным jobs, не интерфейсу. Не коммитьте `.env.local`.

Для нового удалённого проекта сначала проверьте миграции на staging, затем выполните `supabase login`, `supabase link --project-ref <project-ref>`, проверьте `supabase db push --dry-run` и примените `supabase db push`. Эти команды здесь не выполнялись. Каталог можно загрузить отдельно через SQL Editor из `supabase/seed.sql` однократно. Не запускайте production seed с тестовыми пользователями.

### Модель и доступ

- `users.id` связан с `auth.users.id`; Telegram ID уникален, доступен только серверу. Регистрация профиля должна происходить доверенным сервером после будущей проверки Telegram и получения Supabase Auth identity. После проверки initData сервер создаёт профиль и сессию.
- Каталог: `languages → courses → units → lessons → exercises → exercise_options`. Позиции уникальны в родителе. Поддерживаются шесть типов упражнений (см. ниже). Для старых `single_choice` без `public_payload` минимум два варианта и ровно один правильный ответ проверяются отложенными constraint triggers при commit. Редактируйте такой вопрос и варианты одной транзакцией.
- `user_progress` хранит завершённые уроки и лучший результат; `lesson_attempts` — попытки. `xp_events` — источник начисленного опыта, а не изменяемый счётчик на пользователе. Награда выдаётся один раз за урок, независимо от количества попыток.
- `daily_streaks` — уникальные дни активности в закреплённом часовом поясе пользователя; исторические записи до миграции 006 сохраняют UTC. `achievements` и `user_achievements` — каталог и награды; `referrals` запрещает самоприглашения и повторного приглашённого; `subscriptions` хранит интервалы и допускает не более одной активной записи на пользователя. Истёкшие статусы должен обновлять будущий доверенный job; одного `status=active` недостаточно для проверки доступа — учитывайте даты.
- На всех 15 таблицах включён RLS. `anon`/`authenticated` читают только активные языки и опубликованные курсы/уроки с проверкой всей цепочки родителей. Личные таблицы доступны только владельцу по `auth.uid()`, referrals — одному из двух участников. Публичного рейтинга с персональными данными пока нет.
- У браузера **нет INSERT/UPDATE/DELETE**. Нельзя менять XP, завершения, достижения, серии или подписки. Правильность вариантов (`is_correct`), объяснения заданий, Telegram ID и provider reference не выдаются клиенту: используются column grants, поэтому `select('*')` на таких таблицах запрещён. Запрашивайте только разрешённые столбцы.
- `award_completed_lesson(uuid)` доступна только `service_role`: блокирует завершённую попытку и атомарно обновляет XP, прогресс и UTC-день. Повторный вызов возвращает `false` без дублирования XP. Счёт и статус попытки вычисляет `submit_lesson_answer`; браузер не задаёт score или XP. Публичного HTTP endpoint для прямого вызова награды нет.

### Серверные методы

`src/lib/supabase/server.ts` помечен `server-only`: `getMyLearningSummary(token)` проверяет Supabase access token через `auth.getUser`, выводит identity из проверенного токена и использует RLS без service key. `getPublishedCourses()` возвращает ограниченную публичную проекцию. Клиенты создаются на запрос, сессии не разделяются и не сохраняются.

`src/lib/supabase/admin.ts` — только внутренний вызов RPC для внутренних доверенных jobs. Не экспортируйте его через общедоступный маршрут. Service key обходит RLS и требует отдельного контроля серверного вызова. Платёжных webhook и реальных подписок нет; Telegram webhook и проверка initData описаны выше. Игровая оболочка использует `features/demo`; уроки работают через защищённые серверные API.

### Проверки базы без Docker и секретов

```bash
npm ci
npm run test:db
```

Тест поднимает изолированный in-memory PostgreSQL, применяет все миграции и seed, проверяет RLS между двумя пользователями, сокрытие черновиков/ответов, запрет клиентских записей и RPC, FK/check/trigger ограничения и повторное начисление XP. Тестовые identity существуют только в памяти теста.

## Подключение бота @Voklumi_bot

Bot API подтвердил username `Voklumi_bot` для предоставленного токена. Имя Voklumi и команда `/start` уже установлены через Bot API; webhook и кнопка пока не активированы. Код проекта обрабатывает `/start`. Для нового бота используйте `/newbot`, для существующего — его токен. Токен из переписки **не записывался** в файлы проекта, Git или клиентский код. Введите его самостоятельно в секреты хостинга либо в игнорируемый `.env.local`.

1. Разместите Next.js на HTTPS-домене, задайте канонический `APP_URL=https://your-domain.example` (без пути) и Supabase env. Примените миграции, включая `202611020003_telegram.sql`.
2. Задайте `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME=Voklumi_bot` и случайный `TELEGRAM_WEBHOOK_SECRET` (32+ символов, допустимы a-z/A-Z/0-9/_/-). Это три разные настройки; секрет webhook не равен bot token.
3. В BotFather настройте `/setdomain` и Mini App через `/newapp` или настройки бота с тем же HTTPS URL. Для прямой Mini App ссылки может потребоваться отдельный short name; username бота не является доменом приложения.
4. После настройки production env выполните `npm run telegram:setup` из окружения с `.env.local`. Скрипт использует env, задаёт имя Voklumi, команду `/start`, кнопку меню и webhook `/api/telegram/webhook`. Скрипт **не запускался** здесь: публичный HTTPS URL не предоставлен.
5. Напишите боту `/start` в приватном чате. Он отправит кнопку `web_app` «Открыть Voklumi». Webhook проверяет секретный заголовок Telegram, ограничения размера и тип чата; ошибки Bot API не раскрывают токен. Доставка Telegram — at-least-once: при редком повторе update возможно повторное приветствие, финансовых операций здесь нет.

Имя Voklumi_bot само по себе не позволяет настроить webhook. Удалённая Supabase, production webhook, кнопка и реальный мобильный Telegram не проверялись. Локальные тесты не заменяют проверку входа и Back Button на Android/iOS после размещения.

Сессии `telegram_sessions` закрыты RLS и доступны только серверу. По расписанию удаляйте истёкшие записи; уникальные hash можно удалять после истечения сессии (срок initData уже истёк). Не логируйте initData, cookies, bot API URL с токеном или service key. На хостинге настройте лимиты запросов к auth/webhook на уровне reverse proxy. Если сервер завершится между созданием Auth identity и RPC, может остаться неиспользуемая случайная Auth identity: удаляйте такие orphan-записи отдельной обслуживающей задачей. Существующие Auth identities никогда не удаляются при ошибке повторного входа.

## Безопасная локальная авторизация

Не связана с `NEXT_PUBLIC_ENABLE_LOCAL_DEMO`. Для тестовой сессии нужны одновременно `NODE_ENV=development`, loopback hostname, `ENABLE_LOCAL_AUTH=true`, `LOCAL_AUTH_SECRET` длиной не менее 32 символов и совпадающий Origin. Секрет не должен иметь префикс NEXT_PUBLIC_.

Запустите `npm run dev`, затем отправьте локальный POST `/api/auth/local` с заголовками `Origin: http://localhost:3000` и `X-Local-Auth-Secret: <ваш локальный секрет>` (например, через DevTools или REST-клиент). Ответ выставит отдельную подписанную cookie на час. Она создаёт только identity `local-demo` в памяти ответа, не пишет в Supabase и никогда не принимается в production. Не используйте локальный секрет в общем туннеле. Выход — `/api/auth/logout` с тем же Origin.

Проверки: `npm run test:auth` (подпись, подмена, срок, пользователь, Origin, изоляция dev), `npm run test:db` (профиль, сессия, защита от replay и RLS), `npm run build && npm run test:ui` (интерфейс и production-маршруты авторизации).

## Серверный движок уроков

Миграция `202611020004_lesson_engine.sql` расширяет `exercises`, добавляет закрытые таблицы `lesson_attempt_items` (снимок заданий) и `exercise_submissions` (принятые ответы). На обеих таблицах RLS, у anon/authenticated нет чтения или записи. Новые `answer_key` и `public_payload` не выдаются прямым клиентским SELECT; публичные DTO строит сервер по белому списку.

### Запуск

Для новой локальной Supabase выполните `supabase db reset` (удаляет локальные данные): seed добавит старый совместимый урок и новый урок из шести заданий. Для существующей базы примените миграцию и отдельно второй блок `BEGIN…COMMIT` из `supabase/seed.sql` однократно (новый урок), не выполняя весь seed повторно. Стандартный URL `/lesson` выбирает учебный урок `40000000-0000-0000-0000-000000000002`. Другой урок: `/lesson?lesson=<uuid>`.

Нужны настроенная Supabase, service-role key и подтверждённая Telegram-сессия. Нельзя подставить локальную тестовую identity в реальную базу: local-auth получает 403 на lesson API. Без подключения/авторизации UI показывает ошибку, не выдумывает успешное сохранение. Удалённая Supabase и реальный Telegram WebView на этом этапе не проверялись.

### Контракты упражнений

В `public_payload` хранятся только видимые данные. IDs в массивах уникальны; массивы — от 2 до 30 элементов. `answer_key` и `explanation` — серверные данные; объяснение отправляется только после принятия ответа. Новое содержимое и ключ валидируются перед созданием попытки, некорректный или пустой урок не запускается.

| kind          | public_payload                              | answer_key                | Ответ клиента                |
| ------------- | ------------------------------------------- | ------------------------- | ---------------------------- |
| single_choice | options: [{id,label}]                       | value: optionId           | строка optionId              |
| sentence      | tokens: [{id,label}] в перемешанном порядке | value: [tokenId,…]        | упорядоченный массив tokenId |
| gap           | sentence с пропуском                        | accepted: [строка,…]      | строка                       |
| matching      | left/right: [{id,label}]                    | pairs: {leftId:rightId,…} | объект всех пар              |
| grammar       | options: [{id,label}]                       | value: optionId           | строка optionId              |
| listening     | text, lang, options: [{id,label}]           | value: optionId           | строка optionId              |

Gap сравнивается без учёта регистра и лишних пробелов, без удаления пунктуации. Sentence проверяет последовательность IDs; matching требует полную биекцию (каждый перевод используется один раз). Лишние, неизвестные или дублированные IDs не принимаются. Legacy `exercise_options` по-прежнему поддерживаются для старых single_choice.

Web Speech API запускается по нажатию пользователя; поддержаны повтор, остановка, ошибка синтеза, отсутствие API и явный текстовый режим. Голоса и поведение зависят от устройства; native TTS реально не проверен на iOS/Android. Текст для browser TTS неизбежно доступен клиенту — это учебное аудирование, не механизм сокрытия транскрипта. Правильный вариант/ключ на клиент не отправляется. Платных API нет.

### Транзакции и защита

- `POST /api/lessons/start`: `{lessonId, requestId}`. requestId — UUID, повтор запроса не создаёт новую попытку. Публикация языка/курса/урока проверяется сервером; снимок содержания и XP фиксируется при старте. До 100 заданий, до 10 незавершённых попыток на пользователя; старые попытки старше суток очищаются в статус abandoned при последующем старте.
- `GET /api/lessons/<attemptId>`: текущее задание, счётчики и результат. URL с `attempt` позволяет продолжить после перезагрузки. Владелец определяется исключительно из серверной сессии, клиентский userId не принимается.
- `POST /api/lessons/<attemptId>/answer`: `{position, answer}`. Проверка и запись происходят под блокировкой строки попытки. Нельзя отвечать вне очереди. Один ответ на задание: идентичный повтор идемпотентен, попытка заменить уже принятый ответ даёт 409. Объяснение появляется после проверки, но перебрать варианты в этой попытке уже нельзя.
- Последний ответ атомарно завершает попытку, вычисляет score, сохраняет лучший результат и день активности в часовом поясе пользователя и начисляет награды по правилам геймификации. Баллы/XP/статус от клиента не принимаются. С миграции 006 для наград требуется результат от 60%; повторные прохождения могут улучшить best_score и поддержать серию, но XP за один урок выдаётся только раз.
- Таблицы ответов и снимков не имеют клиентских политик/грантов; RPC разрешены только service_role. HTTP слой проверяет Origin, сессию, идентификаторы, допустимые поля и ограничивает размер тела. Возвращаются только публичные поля текущего задания и уже принятая обратная связь. Прямая функция наград остаётся внутренней.

## Геймификация

Миграция `202611020006_gamification.sql` подключает начисления к той же транзакции, которая принимает последний ответ и завершает урок. Примените её перед запуском обновлённого сервера. Удалённая база в этой задаче не менялась.

### Прозрачные правила

| Событие                                                             | XP                                                 | Монеты                             |
| ------------------------------------------------------------------- | -------------------------------------------------- | ---------------------------------- |
| Первый зачёт урока с результатом от 60%                             | Награда урока, зафиксированная при старте (0–1000) | 5                                  |
| Повторный зачёт                                                     | 0                                                  | 0 за сам урок                      |
| Ежедневная цель: 1 впервые зачтённый урок                           | 0                                                  | 10                                 |
| Ежедневная цель: 3 впервые зачтённых урока                          | 0                                                  | 20 дополнительно                   |
| Все опубликованные уроки блока зачтены от 60%                       | 0                                                  | 50, один раз за блок               |
| Все опубликованные уроки курса зачтены от 60%                       | 0                                                  | 100, один раз за курс              |
| Достижения: первый урок / серия 7 дней / 1000 XP / 10 разных уроков | 0                                                  | 15 / 50 / 25 / 30, каждое один раз |

При результате ниже 60% попытка и лучший результат сохраняются, но XP, монеты, активность серии и ежедневные цели не начисляются. Повторение ранее зачтённого урока от 60% поддерживает серию, но не выполняет цель на **новые** уроки. Награды выдаются автоматически, кнопки «получить повторно» нет. Названия/размеры наград задаются сервером.

Уровень `L` начинается с `50 × (L − 1) × L` суммарных XP: 1 → 0, 2 → 100, 3 → 300, 4 → 600, 5 → 1000. Между порогами вычисляется прогресс; до достижения следующего порога он не округляется до 100%. Награды за цели/разделы — только монеты, поэтому они не образуют циклическую генерацию XP. Число источников XP ограничено опубликованными уроками, и один lesson ID приносит XP лишь однажды, независимо от количества попыток и повторов HTTP-запросов.

### Часовой пояс и streak

Новые пользователи начинают с UTC. В профиле до первого зачтённого занятия можно выбрать IANA-зону (например, Europe/Moscow или America/New_York), в том числе определить её по устройству. Сервер проверяет имя через PostgreSQL `pg_timezone_names`. После первого дня активности зона фиксируется; смена требует отдельной контролируемой административной процедуры, которой в приложении нет. Это намеренное ограничение защищает календарь целей и наград от переключения часовых поясов.

День определяется серверным `completed_at AT TIME ZONE time_zone`, а не временем/датой клиента. Дни уникальны по пользователю и календарной дате. Серия сохраняется, если последнее занятие было сегодня или вчера; после пропуска календарного дня текущая серия обнуляется, рекорд остаётся. DST учитывается правилами PostgreSQL: календарные дни могут длиться 23 или 25 часов. Цели сбрасываются в местную полночь, а не через 24 часа от занятия. Смена зоны и завершение урока сериализованы одной блокировкой пользователя.

Исторические XP и UTC-дни сохраняются; пользователи с прежней активностью остаются в UTC. Завершённые до миграции попытки помечаются обработанными без автоматической массовой выдачи монет. Новые квалифицирующие занятия могут открыть ещё не выданные достижения/бонусы разделов. Изменение опубликованного состава блока не переиздаёт уже полученную награду за тот же ID.

### Сервер и защита

`coin_events` — журнал начислений виртуальной валюты; баланс вычисляется как сумма. Уникальный `(user_id, source_key)` защищает каждую награду: урок, дата+цель, достижение, блок или курс. У `xp_events` уже есть уникальный `(user_id, lesson_id)`, у достижений и дней — свои уникальные ключи. `gamification_processed` и сохранённый `reward_summary` делают повторную обработку завершённой попытки безопасной. После перезагрузки показывается сохранённая награда этой попытки, нового начисления не происходит.

Начисления блокируют сначала пользователя, затем попытку — тот же порядок используется при старте, сдаче ответа и выборе зоны. XP, монеты, день активности, достижения, прогресс и бонусы разделов изменяются атомарно. Любая ошибка откатывает все изменения. Клиент не задаёт XP, score, дату, монеты или user ID. Нельзя выиграть дополнительные награды повторным завершением того же урока или новым requestId. Это ограничивает накрутку повторными запросами; не является защитой от автоматического решения разных заданий.

RLS допускает только чтение собственных монет для Supabase Auth-пользователей; записывать журнал или вызывать начисляющие RPC из anon/authenticated нельзя. Telegram-приложение использует серверную сессию: `GET /api/game` возвращает только собственную сводку с no-store, `POST /api/game/timezone` проверяет Origin, identity и блокировку зоны. В локальном тестовом входе реальные награды не выдаются.

Профиль и достижения больше не показывают вымышленные показатели. Без входа виден запрос авторизации; при ошибке — повтор загрузки. Монеты не имеют денежной стоимости; покупки и расходы на этом этапе отсутствуют. Главная и карта остаются явно демонстрационными; их перевод на реальные данные — отдельный этап.

### Сеть и применение миграций

Разрешите исходящий HTTPS к API выбранного Supabase проекта и, при использовании CLI, к Supabase Management API. Для `db push` также требуется разрешённый PostgreSQL TCP-доступ к DB/session-pooler host на порту 5432. В текущем окружении HTTP-политика unrestricted, но список TCP-доменов пуст: это **не подтверждает** возможность прямого PostgreSQL-соединения. Не отключайте TLS и не обходите proxy; при необходимости добавьте разрешение через настройки среды.

После настройки CLI (установленного по официальной инструкции Supabase) и env выполните из текущего репозитория:

```bash
supabase link --project-ref "$SUPABASE_PROJECT_REF"
supabase migration list --linked
supabase db push --linked --dry-run
supabase db push --linked
npm run db:check
```

CLI использует `SUPABASE_ACCESS_TOKEN` и `SUPABASE_DB_PASSWORD` из окружения; не передавайте пароль или полную строку с паролем через аргументы команд. Перед применением к базе с существующими данными подготовьте backup и проверьте dry-run/staging. Не используйте `db reset` для удалённой базы с нужными данными. Миграции применяются по порядку, уже применённые не пересоздаются. Не выполняйте `migration repair` вслепую при несовпадении истории.

Если прямой доступ к PostgreSQL недоступен, администратор проекта может последовательно применить подготовленные SQL-файлы через Supabase SQL Editor. При этом нужно отдельно согласовать историю миграций с CLI перед следующим `db push`; повторный запуск схемы поверх существующих таблиц не является безопасной заменой истории. Публикация 30 уроков — отдельная команда `npm run content:import`, после миграций; автоматического импорта при запуске приложения нет.

### Проверка соединения и защита

`npm run db:check` загружает env текущего процесса и опциональную игнорируемую `.env.local`. Проверка выполняет только read-only RPC `voklumi_database_status`. Код выхода: 0 — все проверки успешны, 1 — сеть/ключ/схема/права не готовы, 2 — конфигурация отсутствует или некорректна. URL, токены, данные пользователей и исходные ошибки Supabase не печатаются. Текущий код ожидает миграцию 010 и проверяет 22 таблицы, RLS, клиентские write grants, закрытые таблицы/столбцы и доступ к основным привилегированным RPC. Проверка включённого RLS не заменяет тесты семантики пользовательских политик.

Для мониторинга есть `GET /api/health/database` с `Authorization: Bearer <SUPABASE_HEALTHCHECK_SECRET>`. Без настройки секрета маршрут отключён (404), с неверным секретом — 401, при проблеме БД — 503. Успех возвращает только статус и версию схемы. Не вставляйте настоящий bearer-секрет в журналируемые команды; монитор должен читать его из secret store. `/api/health` остаётся проверкой процесса и не выдаётся за проверку PostgreSQL.

Серверный клиент централизован в `src/lib/supabase/service.ts`: server-only, без сохранения сессий, с таймаутом и no-store. Отдельного небезопасного «сохранить произвольные XP/progress» endpoint нет.

## Социальные функции

Миграция `202611020008_social.sql` добавляет серверные рейтинги, добровольное участие, реферальную атрибуцию и бонусы. Название приложения остаётся Voklumi.

- `/leaderboard` — неделя или всё время, страницы по 20 игроков и собственная позиция даже вне первой страницы. Неделя едина для всех: понедельник 00:00 UTC до следующего понедельника, конец интервала исключается. Используются только серверные `xp_events`. Участники с нулём XP за период не отображаются. Равные XP дают одинаковое место; порядок внутри равенства стабилен. Рейтинг доступен вошедшим пользователям.
- Профиль скрыт по умолчанию, включая уже зарегистрированных. Пользователь сам выбирает публичный псевдоним и подтверждает участие. Другие игроки получают **только** псевдоним, XP, место и признак собственной строки. В публичные DTO не входят Telegram ID/username, реальное имя, аватар, внутренний user ID, реферальный код или статистика другого игрока. Псевдоним не должен содержать контакты/ссылки; автоматического переноса Telegram-имени нет. Выход из рейтинга исключает профиль из обеих таблиц.
- `/friends` — личная ссылка, копирование, пользовательская кнопка Telegram Share и сводные счётчики присоединений, квалификаций, выплаченных бонусов и монет. Это приглашения, не автоматически созданная двусторонняя дружба; чужие имена и контакты не раскрываются. Отправка приглашения происходит только по действию пользователя. Приложение не отправляет сообщения контактам самостоятельно.

### Реферальная цепочка

`https://t.me/<bot>[/<short-name>]?startapp=r_<случайный-код>` создаётся сервером. Используется `TELEGRAM_BOT_USERNAME` и необязательный `TELEGRAM_MINI_APP_SLUG`; без short name нужна настроенная Main Mini App бота. Настройте её HTTPS URL в BotFather; этот этап не размещает сайт и не заменяет проверку ссылок на реальных клиентах Telegram.

Telegram включает `start_param` в подписанные `initData`. Валидатор извлекает код только после проверки HMAC и срока; неподписанные query-параметры, переданный клиентом referrer/user ID и произвольный URL не принимаются. `create_social_telegram_session` атомарно создаёт сессию, закрепляет атрибуцию новой регистрации и закрывает возможность последующей смены пригласившего. Существующие аккаунты (включая созданные старым RPC) не могут присоединиться задним числом. Один приглашённый — один пригласивший; self-referral запрещён и условием сервера, и CHECK в БД.

Сам переход/регистрация **не даёт награду**. При первом результате приглашённого от 60% триггер в транзакции начисления урока отмечает квалификацию и выдаёт пригласившему **25 монет**, без XP. Не больше **10 оплаченных приглашений за всё время** (250 монет). Лимит определяется журналом выплат и не обнуляется при удалении приглашённого. Повторный урок, повторный ответ, повтор авторизации и другой requestId не создают второй бонус.

Все операции сериализуются блокировкой пригласившего; уникальный источник монет — referral ID. Ошибка выплаты откатывает весь вызов завершения вместе с квалификацией, XP и монетами приглашённого. Квалифицированные сверх лимита учитываются в статистике, но не оплачиваются. Такой лимит ограничивает ущерб от мультиаккаунтов; он не доказывает, что разные Telegram-аккаунты принадлежат разным людям.

### Приватность и API

`GET /api/social?scope=weekly|global&offset=0` возвращает публичную страницу и **собственные** настройки/счётчики. Identity берётся только из HttpOnly-сессии. `POST /api/social/privacy` принимает лишь `{visible, alias}` и проверяет Origin. RPC доступны только service_role; прямое клиентское чтение referrals и чужого attempt ID в coin_events отозвано. Журнал наград хранит непрозрачный referral ID, а при удалении исходной попытки ссылка очищается, сохраняя денежный итог без чужих персональных данных.

`npm run test:social` проверяет атрибуцию, позднее присоединение, self/duplicate/retry, полезное действие, лимит и удаление аккаунта, откат награды, согласие и выход, UTC-границы, равенства, страницы, собственную позицию и закрытые DTO/RLS. `npm run test:auth` проверяет подпись start_param и допустимые Telegram URLs. Браузерные тесты используют настоящие SQL RPC с тестовой подменой transport/auth и проходят мобильный рейтинг, настройки и шаринг. Реальное открытие приглашения в Telegram требует развёрнутой Mini App.

Миграция 008 применена к удалённому проекту; серверная readiness-проверка вернула `ready: true`, `schemaVersion: 202611020008`. Данные курсов не менялись, тестовые социальные профили/связи в удалённую БД не добавлялись. Полный переход по приглашению в мобильном Telegram пока не проверялся.

## Premium и Telegram Stars

`/premium` показывает Free/Premium, подтверждённый сервером срок доступа, условия покупки, поддержку, статистику и план повторения. Переход доступен из профиля; существующий дизайн сохранён. Premium — разовая покупка **30 дней без автопродления**. Цена не назначена автоматически.

Реальные покупки **выключены**. Для запуска недостаточно одного токена: нужны оба флага `TELEGRAM_STARS_PAYMENTS_ENABLED=true` и `TELEGRAM_STARS_OWNER_REVIEWED=true`, серверные секреты, утверждённая цена и HTTPS-страницы условий/поддержки. Локальная авторизация не может создавать платежи или получать реальные Premium-права.

Миграция `202611020009_stars.sql` подготовлена и проверяется локально. **Она не применена к удалённой Supabase**: последняя подтверждённая удалённая версия — 008, 19 таблиц. Перед размещением этого кода примените 009 на staging, затем после проверки к нужной базе: Stars требуют 009; текущая readiness-проверка с административной панелью требует 010 и 22 таблицы. Само применение схемы не включает оплату и не закрывает существующие курсы. Файл `supabase/premium-policy.sql` отдельно переводит тематические курсы в Premium с двумя бесплатными уроками каждого; это ручная политика после проверки владельцем, а не автоматическая миграция.

Счёт, сумма и покупатель связываются на сервере. Только проверенный webhook `successful_payment` выдаёт доступ; pre-checkout и клиентский callback этого не делают. SQL-транзакции, уникальные charge ID и блокировки защищают повторную обработку. Подтверждённый возврат отзывает соответствующий период, окончание срока проверяется при каждом доступе к уроку. Новые платежи можно отключить, сохранив обработку ранее подтверждённых оплат/возвратов.

```bash
npm run test:payments
npm run test:ui
```

Подробная схема, официальные ссылки Telegram, переменные окружения, проверка владельцем, безопасный возврат и ограничения проверки — в [docs/TELEGRAM_STARS.md](docs/TELEGRAM_STARS.md).

## Административная панель

`/admin` и ссылка в профиле открывают серверно защищённую панель: ученики, контент (курсы → разделы → уроки → шесть типов заданий), учебная активность, статистика, просмотр подписок и журнал изменений. Формы поддерживают черновики, публикацию, Free/Premium и бесплатные превью.

Доступ задаётся **только серверной конфигурацией `ADMIN_USER_IDS`** — внутренние UUID проверенных Telegram-профилей через запятую. Пустое/неверное значение закрывает доступ. Ни локальная авторизация, ни клиентская роль прав не дают. Каждый API-запрос проверяет сессию и allowlist; сохранения дополнительно требуют Origin, строгую валидацию, подтверждение и текущую версию записи. Изменение и аудит сохраняются транзакцией, повторы идемпотентны.

Миграция `202611020010_admin.sql` подготовлена, локальные тесты проверяют **22 таблицы**. Удалённо 009/010 не применялись; последнее подтверждённое удалённое состояние остаётся 008. Перед размещением нужны недостающие миграции и серверные переменные окружения. Реальные платежи остаются выключенными.

```bash
npm run test:admin
npm run test:ui
```

Настройка первого администратора, возможности, публикация и границы безопасности описаны в [docs/ADMIN.md](docs/ADMIN.md).
